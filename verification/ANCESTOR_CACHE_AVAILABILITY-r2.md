# Cache retention requires a finalized snapshot

Root review of the first ancestor-cache candidate found an availability flaw: a failed exact-key guard skips replication, but an unconditional cache-maintenance step could still prune and save restored staging that the harness never validated. A second, independently noticed path was an attempted replication that failed before project/context initialization: its `finally` block would not produce a snapshot, leaving the old staging manifest intact.

The revised workflow gates maintenance on an attempted replication outcome of `success` or `failure`, excluding `skipped` and `cancelled`. Before invoking any maintenance, trusted inline code also requires this invocation's `finished.json` with the expected schema and proof, an `owned_cache` receipt for that proof with status `ready`, and a declared manifest SHA equal to the actual staging manifest bytes. Missing, malformed or mismatched receipts skip maintenance. Thus no new snapshot means no prune/save; a genuine finalized partial-build snapshot remains eligible even when replication failed. Save and backend-audit steps still depend on maintenance's `ready` output.
