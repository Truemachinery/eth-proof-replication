# Public Linux replication pipeline

This bundle is a prepared workflow, not a completed replication result. Install the byte-identical `workflow-template.yml` as `.github/workflows/replicate.yml` in the new **public** repository, and copy only the listed `ci/` files. It runs solely through `workflow_dispatch` on standard `ubuntu-24.04` GitHub-hosted runners. It never dispatches itself, publishes a proof verdict, uploads Actions artifacts, uses larger runners, raises cache allowances or accesses mining infrastructure.

Two explicit jobs independently acquire the public inputs in `pins.json`. Each has a 350-minute job cap, a 330-minute harness deadline and a controlled source-build stop with 15 minutes reserved before that deadline for snapshotting. Source compilation uses two admitted Lean frontends, each with two runtime threads. This bounds frontends, not every C/link process. A 14 GiB systemd memory limit, real Landrun, non-root checker identity and `RestrictAddressFamilies=~AF_UNIX` apply to source compilation and configured checker services. The ordinary real-prefix no-build Lake trace check evaluates the trusted package configuration outside Landrun; fresh leanchecker itself runs inside read-only Landrun. Enforcement controls must succeed; there is no fake-Landrun fallback. Exact source bytes and compiler arguments are preserved.

The runner downloads fixed-version official Lean release archives and records their SHA-256 and runtime binary/library identities; expected archive byte hashes are not pre-pinned. Tool source commits and Cargo's lockfile are pinned. Go/Rust/C compiler versions and host inventory are recorded; the hosted image is a moving dependency. Mathlib's official cache is downloaded for the exact locked dependency revision. Trust in these distribution channels/cache is disclosed; this is not a bootstrap of all compilers or a complete Mathlib source rebuild.

OpenAI uses a minimal Lake package with the byte-identical lexical source closure (3091 OAI files plus one challenge file), exact 4.34.1 toolchain, exact Mathlib pin and `autoImplicit=false`; unrelated upstream packages are omitted. That is a recorded package-configuration deviation. Anthropic uses its unchanged `eth/` package, lockfile and 4.33.1 toolchain, including all default source targets. Its upstream Comparator 575 is built at its own 4.34.0-rc1 toolchain; OpenAI uses reviewed Comparator 865 built at 4.35.0. Exporter `.0` source commits are compiled with the respective proof's `.1` compiler, following the upstream documented patch fallback.

`all` continues from any matching owned-output cache, builds sources and attempts the checks. `build` stops after successful ordinary source/trace checks and records **checks pending**. `verify` requires complete normal Lake build traces from a validated cache and runs the checks without intentionally compiling missing project modules. An incomplete build makes that mode fail. Repeat a manual `build`/`all` run to continue a source build, then use `verify` for the full checking budget. A timeout or interrupted stage remains incomplete evidence.

The required checking sequence is:

1. Ordinary source build and a real original-prefix `lake --no-build build` trace check.
2. Original-version `leanchecker --fresh` on the solution module's complete import closure.
3. Official Comparator on the original exact challenge/solution target configuration, allowing only `propext`, `Quot.sound` and `Classical.choice`, with no definition holes. Anthropic's original config also invokes pinned Nanoda. OpenAI's original config disables it.
4. A separately labelled selected-target export, with hash/config recorded. OpenAI additionally checks that export through pinned Nanoda with strict axiom rejection. Anthropic's additional export supplies provenance only, since its Comparator already invokes Nanoda.

Comparator's temporary export is deleted by its own implementation and is not archived here. The separately hashed export **does not identify the bytes of Comparator's temporary input**. Large separate exports stay on the ephemeral VM; only their hashes/configs and stage output remain in workflow logs. Exact exit status plus required official success output gate acceptance. A complete positive formal result says nothing by itself about the intended mathematical model or Bitcoin search performance.

`record.py` writes prepared/finished JSON receipts and fsynced raw logs, streams compiler output with a prefix and display-only escapes for legacy command markers and carriage returns, and prints compact hash-bound receipts. Recorded child CPU measures reaped subprocesses; it excludes systemd-managed service CPU. Systemd CPU/memory accounting is enabled and its own runtime output is preserved for later accounting; do not sum the child counters as total proof CPU. Timeout kills the direct process group; systemd services also have independent runtime/stop limits and control-group teardown. A platform-forced VM kill can prevent a finished receipt. Such a stage is incomplete. GitHub log truncation/retention limits can also prevent later retrieval of all streamed output; retain downloaded logs separately after a run.

Only project-owned, completed normal build artifacts and traces may enter the Actions cache. Toolchains, Mathlib/dependency builds, proof sources, exports, credentials and other project material are excluded. A SHA manifest binds each restored file to exact project sources/config, harness pins and proof runtime identities. Normal traces are checked again and fresh independent checks are required; cache integrity is not a proof verdict. A payload exceeding 2 GiB, including manifest/overhead reserve, is skipped with a receipt. A post-save API audit records actual backend archive sizes; it deletes an oversized new own-proof entry and fails, rather than treating the staging reserve as a formal backend bound. A dedicated token-bearing maintenance step deletes previous snapshots for this proof before saving a unique immutable replacement. It refuses unrelated namespaces/multiple other-proof snapshots, retaining at most one <=2 GiB snapshot per proof (<=4 GiB total). Workflow concurrency serializes manual runs. Cache helpers require the fixed trusted cache/project paths supplied by this workflow; they are not an API for untrusted destination paths. Do not raise the repository's included cache allowance. The cache API token is used only by that trusted maintenance step; it is absent from every proof/build/checker subprocess environment.

Four fixed SDK directories may be deleted **only after** the public/manual/non-root disposable-host guard succeeds: `/usr/local/lib/android`, `/usr/share/dotnet`, `/opt/ghc`, `/opt/hostedtoolcache/CodeQL`. No such cleanup can run locally or on a self-hosted runner. The harness requires 26 GiB free afterward because 14 GiB guaranteed runner disk is insufficient for two Lean installations, Mathlib and large exports. If the image cannot provide that space, the job fails before acquisition.

Local controls in `control-result.json` and `control-result-r2.json` exercise guard rejection, credential removal, recorder success/failure/timeout/export behavior, exact-line acceptance, cache ownership/bounds/drift rejection, and a Darwin control compile of the otherwise equivalent C gate. The second result also covers real module-mode Lake build/cache/restore/no-build roundtrips at both exact proof toolchains, including a missing-IR-signature negative control. The initial cache whitelist omitted IR signatures; independent review found it before publication and the correction is covered by those real controls. They do not test Linux OpenSSL compilation, systemd/Landrun support or either proof. Two earlier local control failures (temporary-path alias handling and Darwin feature macros) were corrected and their raw logs remain in the private preparation record. No proof was run by these controls.

Revision 2 adds only module-owned `ir/<module>.bc` and `.bc.hash` to the cache whitelist. Both pinned Lake versions define `bcFile` in the package IR directory and conditionally require/cache it when `Lean.Internal.hasLLVMBackend()` is true. The new `check_bc_control.py` / `control-result-bc-r2.json` exercise path/module ownership, exact-byte restore, tamper rejection and the unchanged size bound using synthetic artifact bytes. They do not establish whether official Linux releases enable LLVM or validate LLVM output. The prior frozen public revision 1 remains unchanged; this is a separate export revision.

Revision 3 fixes the versioned stage-name validator after both jobs of run 41888029999 failed before downloading Lean. It also excludes generated `.setup.json` compiler-input inventories from continuation caches. Pinned Lake constructs and writes those inventories immediately before compilation; they are absent from its required output-artifact check. The exact candidate omission passed tiny real native Lean 4.34.1 and 4.33.1 controls: restore without inventories, normal `lake --no-build build`, ordinary resume with restored output bytes/mtimes unchanged, compilation of one new dependent (only its own inventory generated), and final no-build check. `check_setup_omission_control.py` and `control-result-setup-omission-r3.json` preserve this scoped evidence. Normal object files, IR, interfaces, hashes and traces, including conditional owned LLVM bitcode, remain under the same ownership, integrity and 2 GiB bound. The cache size for the entire proof remains unmeasured; large generated inventories cannot by themselves force this cache over its cap now. These controls do not constitute Linux or ETH proof verification.

The revision 3 logging correction follows the [runner2.338.2 legacy parser](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Common/ActionCommand.cs#L119) and its [fallback call](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Worker/ActionCommandManager.cs#L62): a prefix alone does not block legacy markers appearing later in a line. `record.py` now escapes literal legacy markers and carriage returns in displayed text only. `check_display_control.py` / `control-result-display-r3.json` verify that raw bytes, raw/export hashes, exact raw success-line checks and child exit semantics remain unchanged. This is a local regression against the inspected parser behavior, not GitHub runner execution. No hostile output was observed in the initial Linux run.
