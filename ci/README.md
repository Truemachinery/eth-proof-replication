# Public Linux replication pipeline

This revision is a prepared repair candidate, not a completed replication result. Its public layout contains `.github/workflows/replicate.yml` and the fixed `ci/` inputs. It runs solely through `workflow_dispatch` on standard `ubuntu-24.04` GitHub-hosted runners. It never dispatches itself, publishes a proof verdict, uploads Actions artifacts, uses larger runners, raises cache allowances or accesses mining infrastructure.

Two explicit jobs independently acquire the public inputs in `pins.json`. Each has a 350-minute job cap, a 330-minute harness deadline and a controlled source-build stop with 15 minutes reserved before that deadline for snapshotting. OpenAI source compilation admits one Lean frontend; Anthropic admits two. Each uses two runtime threads. This bounds frontends, not every C/link process. A 14 GiB systemd memory limit, real Landrun, non-root checker identity and `RestrictAddressFamilies=~AF_UNIX` apply to source compilation and configured checker services. The ordinary real-prefix no-build Lake trace check evaluates the trusted package configuration outside Landrun; fresh leanchecker itself runs inside read-only Landrun. Enforcement controls must succeed; there is no fake-Landrun fallback. Exact source bytes and compiler arguments are preserved. One frontend is a response to the observed OpenAI combined-memory failure; it does not establish that every individual compiler fits the limit.

The runner downloads fixed-version official Lean release archives and records their SHA-256 and runtime binary/library identities; expected archive byte hashes are not pre-pinned. Tool source commits and Cargo's lockfile are pinned. Go/Rust/C compiler versions and host inventory are recorded; the hosted image is a moving dependency. Mathlib's official cache is downloaded for the exact locked dependency revision. Trust in these distribution channels/cache is disclosed; this is not a bootstrap of all compilers or a complete Mathlib source rebuild.

OpenAI uses a minimal Lake package with the byte-identical lexical source closure (3091 OAI files plus one challenge file), exact 4.34.1 toolchain, exact Mathlib pin and `autoImplicit=false`; unrelated upstream packages are omitted. That is a recorded package-configuration deviation. Anthropic uses its unchanged `eth/` package, lockfile and 4.33.1 toolchain, including all default source targets. Its upstream Comparator 575 is built at its own 4.34.0-rc1 toolchain; OpenAI uses reviewed Comparator 865 built at 4.35.0. Exporter `.0` source commits are compiled with the respective proof's `.1` compiler, following the upstream documented patch fallback.

`all` continues from any matching owned-output cache, builds sources and attempts the checks. `build` stops after successful ordinary source/trace checks and records **checks pending**. `verify` requires complete normal Lake build traces from a validated cache and runs the checks without intentionally compiling missing project modules. An incomplete build makes that mode fail. Repeat a manual `build`/`all` run to continue a source build, then use `verify` for the full checking budget. A timeout or interrupted stage remains incomplete evidence.

The required checking sequence is:

1. Ordinary source build and a real original-prefix `lake --no-build build` trace check.
2. Original-version `leanchecker --fresh` on the solution module's complete import closure.
3. Official Comparator on the original exact challenge/solution target configuration, allowing only `propext`, `Quot.sound` and `Classical.choice`, with no definition holes. Anthropic's original config also invokes pinned Nanoda. OpenAI's original config disables it.
4. A separately labelled selected-target export, with hash/config recorded. OpenAI additionally checks that export through pinned Nanoda with strict axiom rejection. Anthropic's additional export supplies provenance only, since its Comparator already invokes Nanoda.

Comparator's temporary export is deleted by its own implementation and is not archived here. The separately hashed export **does not identify the bytes of Comparator's temporary input**. Large separate exports stay on the ephemeral VM; only their hashes/configs and stage output remain in workflow logs. Exact exit status plus required official success output gate acceptance. A complete positive formal result says nothing by itself about the intended mathematical model or Bitcoin search performance.

`record.py` writes prepared/finished JSON receipts and fsynced raw logs, streams compiler output with a prefix and display-only escapes for legacy command markers and carriage returns, and prints compact hash-bound receipts. Binary export stdout is copied in 4 MiB chunks with per-chunk and final fsync; textual output retains line-by-line display. Finished receipts preserve an explicit recorder-wait timeout flag and combine a timeout reason with later output-pump errors instead of erasing the original deadline failure. A systemd service can reach its separate runtime limit and fail before the recorder wait expires; its raw result remains separate evidence and the recorder flag can then be false. Recorded child CPU measures reaped subprocesses; it excludes systemd-managed service CPU. Systemd CPU/memory accounting is enabled and its own runtime output is preserved for later accounting; do not sum the child counters as total proof CPU. Timeout kills the direct CLI process group; an independently managed systemd service is bounded separately. The retained export now explicitly receives the same 1800-second outer budget, yielding a service runtime cap of at most 1795 seconds plus a five-second stop limit, subject to the earlier harness deadline. This bounds that particular service without global service kills. A platform-forced VM kill can prevent a finished receipt. Such a stage is incomplete. GitHub log truncation/retention limits can also prevent later retrieval of all streamed output; retain downloaded logs separately after a run.

Only project-owned, completed normal build artifacts and traces may enter the Actions cache. Toolchains, Mathlib/dependency builds, proof sources, exports, credentials and other project material are excluded. A SHA manifest binds each restored file to exact project sources/config, harness pins and proof runtime identities. Normal traces are checked again and fresh independent checks are required; cache integrity is not a proof verdict. Snapshot limits are 6 GiB for OpenAI and 2 GiB for Anthropic, including manifest/overhead reserve. An oversized payload is skipped with a receipt. A post-save API audit records actual backend archive sizes; it deletes an oversized new own-proof entry and fails, rather than treating the staging reserve as a formal backend bound. A dedicated token-bearing maintenance step deletes previous snapshots for this proof before saving a unique immutable replacement. It refuses unrelated namespaces/multiple other-proof snapshots, retaining at most one snapshot per proof within those limits and 8 GiB total. These bounds stay below the repository's previously verified included 10 GB allowance; no purchased limit increase is used. Fixed per-proof job groups permit at most one OpenAI and one Anthropic job, with cancellation disabled. Cache helpers require the fixed trusted cache/project paths supplied by this workflow; they are not an API for untrusted destination paths. The cache API token is used only by that trusted maintenance step; it is absent from every proof/build/checker subprocess environment.

Normal restoration requires the current harness fingerprint. Revision 7 replaces the now-pruned revision 4 exception with exactly one observed Anthropic cache from run `41911047958`, producer commit `309670f70aa79d85752dbdc61799ad8cc56772c2`, recorded in `ancestor-cache-compatibility.json`. It requires the exact full restored key, exact original manifest SHA, unchanged current source/config/proof-runtime context, and the old fingerprint recomputed from the actual 24 producer rows, including that producer's ledger, plus the current context. The new ledger pins the exact current 23 nonledger producer rows and workflow bytes; excluding itself from that row map avoids a circular hash, while the normal current fingerprint still binds the new ledger. Unreviewed changes reject the exception. All ownership, per-file SHA/size and resource checks remain. The old manifest is preserved under runner records and never relabeled; new snapshots receive the ordinary current fingerprint. There is no OpenAI predecessor exception: its observed oversized snapshot was never saved.

Before any cache pruning or saving, the workflow requires an attempted replication outcome and this invocation's finalized `finished.json` with the correct schema/proof, a ready snapshot receipt and an exact staging-manifest SHA match. Missing or mismatched receipts skip maintenance. A failed key guard, cancelled step or failure before snapshot production preserves the previous backend entry; legitimate finalized partial-build snapshots remain eligible.

Both earlier Linux jobs are now terminal. Fixed per-proof job groups enforce one job per proof across manual runs. Preparation of this repair does not start another job; the ongoing native OpenAI replication has priority, and no cold OpenAI Linux retry is part of this revision's validation.

Four fixed SDK directories may be deleted **only after** the public/manual/non-root disposable-host guard succeeds: `/usr/local/lib/android`, `/usr/share/dotnet`, `/opt/ghc`, `/opt/hostedtoolcache/CodeQL`. No such cleanup can run locally or on a self-hosted runner. The harness requires 26 GiB free afterward because 14 GiB guaranteed runner disk is insufficient for two Lean installations, Mathlib and large exports. If the image cannot provide that space, the job fails before acquisition.

Historical local controls in `control-result.json` and `control-result-r2.json` exercise guard rejection, credential removal, recorder success/failure/timeout/export behavior, exact-line acceptance, cache ownership/bounds/drift rejection, and a Darwin control compile of the otherwise equivalent C gate. The second result also covers real module-mode Lake build/cache/restore/no-build roundtrips at both exact proof toolchains, including a missing-IR-signature negative control. The initial cache whitelist omitted IR signatures; independent review found it before publication and the correction is covered by those real controls. They do not test Linux OpenSSL compilation, systemd/Landrun support or either proof. Two earlier local control failures (temporary-path alias handling and Darwin feature macros) were corrected and their raw logs remain in the private preparation record. No proof was run by these controls. Revision 7 preserves those result bytes and narrowly updates two cache-control sources to the new per-proof API; it does not claim a rerun of the historical real-Lean controls. New transport, cache-boundary, actual-driver/service-budget, exact-predecessor and workflow-ready-guard controls are separately versioned under `verification/` and use small local fixtures or mocks without proof execution.

Revision 2 adds only module-owned `ir/<module>.bc` and `.bc.hash` to the cache whitelist. Both pinned Lake versions define `bcFile` in the package IR directory and conditionally require/cache it when `Lean.Internal.hasLLVMBackend()` is true. The new `check_bc_control.py` / `control-result-bc-r2.json` exercise path/module ownership, exact-byte restore, tamper rejection and the unchanged size bound using synthetic artifact bytes. They do not establish whether official Linux releases enable LLVM or validate LLVM output. The prior frozen public revision 1 remains unchanged; this is a separate export revision.

Revision 3 fixes the versioned stage-name validator after both jobs of run 41888029999 failed before downloading Lean. It also excludes generated `.setup.json` compiler-input inventories from continuation caches. Pinned Lake constructs and writes those inventories immediately before compilation; they are absent from its required output-artifact check. The exact candidate omission passed tiny real native Lean 4.34.1 and 4.33.1 controls: restore without inventories, normal `lake --no-build build`, ordinary resume with restored output bytes/mtimes unchanged, compilation of one new dependent (only its own inventory generated), and final no-build check. `check_setup_omission_control.py` and `control-result-setup-omission-r3.json` preserve this scoped evidence. Normal object files, IR, interfaces, hashes and traces, including conditional owned LLVM bitcode, remain under the same ownership and integrity rules. That historical control used a 2 GiB cap; revision 7 changes only the per-proof resource limits described above. These controls do not constitute Linux or ETH proof verification.

The revision 3 logging correction follows the [runner2.338.2 legacy parser](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Common/ActionCommand.cs#L119) and its [fallback call](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Worker/ActionCommandManager.cs#L62): a prefix alone does not block legacy markers appearing later in a line. `record.py` now escapes literal legacy markers and carriage returns in displayed text only. `check_display_control.py` / `control-result-display-r3.json` verify that raw bytes, raw/export hashes, exact raw success-line checks and child exit semantics remain unchanged. This is a local regression against the inspected parser behavior, not GitHub runner execution. No hostile output was observed in the initial Linux run.

Revision 4 follows run 41891445823, which built the pinned tools and dependencies but failed before proof compilation because strict Landrun requested ABI 9 on a hosted kernel reporting ABI 8. The five harness-owned Landrun invocations now explicitly use `--best-effort`, matching the unchanged official Comparator drivers. A read-only Linux x86_64 ABI query requires at least 8 before any cleanup or toolchain acquisition. Pinned Landrun acquisition and mandatory runtime write-denial/socket-creation controls run next, before expensive proof setup. Binary/source pins, path/environment permissions, theorem/axiom policies and resource caps are unchanged.

This is explicitly ABI 8 coverage when that ABI is observed, not full ABI 9. The [pinned Landlock dependency](https://github.com/landlock-lsm/go-landlock/tree/e573f52a61e3072813de11359239d2ccae9705d2) retains its earlier filesystem, classic TCP, IPC-scope and thread-synchronization rights on ABI 8; it omits the ABI 9 pathname UNIX connect/sendmsg right (`RESOLVE_UNIX`). The separate systemd test measures denial of `socket(AF_UNIX)` creation only. It does not cover inherited sockets, `socketpair` or `io_uring`, and is not a complete replacement for ABI 9 pathname-socket mediation. Actual runtime controls must pass on every job. See [pinned Landrun policy](https://github.com/zouuup/landrun/blob/811cfff51ceaf3d9843708aa6d22e9b84ccac8b4/internal/sandbox/sandbox.go) and [systemd's documented limits](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#RestrictAddressFamilies=).

`landlock_abi.py` queries syscall 444 with the version flag 1 only after checking Linux x86_64, following the [Linux 7.0 syscall table](https://github.com/torvalds/linux/blob/v7.0/arch/x86/entry/syscalls/syscall_64.tbl) and [UAPI header](https://github.com/torvalds/linux/blob/v7.0/include/uapi/linux/landlock.h). `check_landlock_policy_control.py` / `control-result-landlock-policy-r4.json` exercise the architecture guard, ABI floor/error handling and exact five-call policy/order using local mocks/static inspection. They do not claim Linux sandbox success. The earlier failed runs and frozen exports remain unchanged.

Revision 6 forwards the existing exact real `LEAN_SYSROOT` into the separately retained export's Landrun environment.
